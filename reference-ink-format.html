The .ink file format

An .ink file is a single SQLite database holding one font project — every master, layer, kerning pair, feature and Font Info field — together with the font's own version history.

What's in a .ink file

  • The database is the font. Ink edits it directly; there is no separate in-memory copy waiting to be saved. UFO, .glyphs, .designspace, OTF and TTF files are written fresh from it on Export.
  • How a file comes to exist. Creating a new font makes a native .ink. Opening a UFO or Glyphs source creates a companion file next to it — Font.ufo gets Font.ufo.ink — and Ink works in that from then on. A compiled OTF or TTF is opened in memory and only becomes a file when you save it as .ink.
  • Mostly plain tables. Relational tables hold the data, with JSON where the structure is irregular (outlines, components, vendor data) and compressed blobs only in the history tables.
  • One version number. The file records a single schema version integer.

Design decisions

SQLite, not text files

Why
Every format Ink reads goes down one data path. Panels query only what they show, writes are atomic and crash-safe, and constraints enforce invariants such as one default layer per glyph.

Trade-off
The file is binary, so git can't diff or merge it line by line. Exchange goes through export.

One file, not a folder

Why
A single file is easy to send, back up and double-click. Operating systems associate an app with a file type far more reliably than with a folder bundle such as .ufo.

Trade-off
While a font is open SQLite keeps a -wal file beside it; close the font before copying the .ink elsewhere.

Import translates, export rewrites

Why
Importers map everything they understand into typed columns, and keep everything else as JSON vendor data on the font, masters, glyphs, layers and instances. Export writes brand-new files, so there is no patching of stale originals.

Trade-off
What no parser can see — comments, formatting, attribute order, a UFO's data/ folder — is not kept.

History inside the file

Why
Time Machine snapshots travel with the font, and a restore rolls back outlines, kerning, anchors and metadata together.

How
Glyph layers are stored as keyframes plus small deltas. Snapshot payloads go into a content-addressed store — identical outlines are stored once, compressed — so a snapshot with no changes costs almost nothing.

Trade-off
History only grows: every snapshot that changes something adds to the file until you clear it. See File size.

Compact outlines

How
Each layer keeps its contours as JSON in one row, with points in a flat positional encoding and persistent point ids. Components carry a full 2×2 matrix and offset.

Why
One row per layer keeps reads cheap; the flat encoding cut outline data by about three quarters.

One layer model

How
Every layer is a master layer, a special layer (brace or bracket), a free-form sketch layer or an image layer. Anchors, guidelines and metric keys belong to a layer, so they can differ per master.

Why
It combines Glyphs' structured interpolation layers with UFO's free-form layers.

Explicit coordinate spaces

How
Axis ranges and instances are stored in user space; masters, brace layers and rule conditions in design space; the axis mapping (avar) bridges them and is checked to keep rising.

See
Font Info → Designspace.

Kerning as design data

How
Groups, group membership and pairs, where each side is a glyph or a group. Every pair has a master and a direction — LTR, RTL or vertical. A glyph belongs to at most one group per side.

Why
It matches the source-format model; OTF and TTF kerning is generated from it on export.

Features as text plus generated code

How
Feature, prefix and class blocks in AFDKO syntax, with Glyphs-style automatic, disabled and notes flags. Kerning and mark attachment are generated from data at export and placed with the # Automatic Code marker.

See
Font Info → Features.

Compiled fonts become source

How
Saving an OTF or TTF as .ink turns its kerning, anchors and GSUB / GPOS lookups back into editable data and feature code. Ink recompiles the result and checks it against the original before keeping it; anything that fails is reported. The original binary isn't kept.

Trade-off
TrueType hinting, colour, bitmap and other unmodelled tables are not carried over.

One writer at a time

How
SQLite runs in write-ahead-log mode with foreign keys on. Ink runs as a single instance and locks each font database it has open.

Why
The real risk is two editors holding diverging in-memory edits of the same font, not database corruption.

Forward-only versioning

How
The file stores one schema version. Opening an older file migrates it forward inside a transaction, then compacts it. A file from a newer Ink is refused with a request to update.

Trade-off
No backward compatibility: an older Ink can't open a newer file.

App settings, undo history, the clipboard and editor session state never go into the file.

File size

The biggest cost of the format: an .ink file is noticeably larger than the same font saved as .glyphs or UFO. Three things add up.

Everything is explicit

Every master's outlines, metrics and anchors are stored in full, and kerning is expanded per master and per direction rather than shared or inferred. Source formats lean on defaults, sparse masters and shared group data instead.

Built for queries

Indexes on glyphs, layers and kerning let Ink read only what it shows — but they take space on disk that a text format doesn't need.

History lives inside

Time Machine snapshots are part of the file. The first snapshot is effectively a second, compressed copy of every outline, and each snapshot after it adds whatever changed. Over a long project, history can outweigh the font itself.

Keeping it in check

  • Unchanged outlines are stored once and compressed, so repeated snapshots of the same state cost almost nothing, and a snapshot with no changes is never written.
  • When history grows past 60% of the file's size, Ink suggests clearing it. Clear history… removes all snapshots and compacts the file — your current font is untouched.
  • To send or archive a font compactly, export it to UFO or .glyphs; neither carries history.
  • While a font is open, SQLite's -wal file can temporarily hold another copy of recent changes until it is checkpointed.

Round-tripping

UFO and .designspace

  • Kept on import: outlines with point and component identifiers; components with their full transform; anchors and guidelines; other layers as sketch layers; groups and kerning (direction inferred from each glyph's Unicode bidi class); features.fea split into blocks; fontinfo into Font Info; lib.plist and glyph libs as vendor data; designspace axes, maps, labels, rules and instances.
  • Lost on import: the data/ folder, XML comments and formatting.
  • On export: a pair present in both LTR and RTL is written once with its LTR value and a warning; vertical kerning isn't written. Generated kern and mark code isn't written as FEA — kerning and anchors are exported as data for the compiler. Disabled feature blocks are written commented out.

.glyphs

  • Kept on import: master, brace, bracket and background layers; per-master LTR, RTL and vertical kerning and groups; features, prefixes and classes with their flags; metric keys, zones, stems, colours, production names; custom parameters and userData.
  • On export: written in the Glyphs 3 format. Designspace rules aren't written yet, and variable feature code uses feaLib syntax, which Glyphs' own syntax may not compile.

Inspecting a .ink file

Any SQLite client can open a .ink file. Open it read-only, and not while Ink is writing to it:

sqlite3 -readonly MyFont.ink .tables SELECT version FROM schema_meta; SELECT g.glyph_name, l.name, l.advance_width FROM glyphs g JOIN glyph_layers l USING (font_id, glyph_id) WHERE l.layer_type = 'master';

JSON columns such as paths_json and vendor_data work with SQLite's json_extract and json_each. History payloads in snapshot_blobs are zstd-compressed.

Stability
  • The format is still evolving before Ink 1.0. Newer Ink versions migrate older files forward on open; older versions refuse files from newer ones.
  • Don't write to a .ink with another tool while Ink has it open.
  • Once a source has been opened, Ink works in its companion .ink and doesn't re-read the original — export when you need the UFO or Glyphs file updated.
